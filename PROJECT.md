# Italian Conversation Tutor — Контекст проекта

> Бот для тренировки разговорной речи на итальянском языке для русскоязычного ученика.
> Этот документ — единый источник истины по принятым решениям. Обновляется по мере развития проекта.
>
> **Статус:** Базовый функционал реализован и работает в проде. iOS Пакет 1-3 готов, прикладные улучшения (Wake Lock, транскрипт, лимит сессии, lifecycle аудио) реализованы. См. раздел 10 (Прогресс реализации) и 11 (Особенности реализации).

---

## 1. Цель и целевой пользователь

**Цель:** дать пользователю возможность регулярно тренировать разговорный итальянский в формате голосового диалога с ботом, с автоматическим разбором ошибок в конце сессии.

**Пользователь:** один человек (личный инструмент), русскоязычный, изучает итальянский. Уровень владения языком задаётся вручную в профиле в формате CEFR (A1–C2) и влияет на сложность речи бота.

**Ключевые функции:**
- Голосовой диалог с ботом на выбранную тему
- Разбор ошибок и обратная связь в конце сессии
- История сессий с возможностью пересмотра ошибок
- Управление уровнем сложности через профиль

## 3. Архитектура голосового слоя

### Текущий режим: turn-based (push-to-talk)

Пользователь нажимает кнопку записи, говорит, отпускает — реплика отправляется на сервер, обрабатывается полным пайплайном и возвращается аудио-ответ. Задержка между репликами 2–4 секунды.

**Пайплайн одной реплики:**
1. Запись на клиенте через `MediaRecorder`
2. POST на Next.js API route
3. Whisper API → текст реплики пользователя
4. Запись в `messages` (role=`user`) в БД
5. GPT-4o с системным промптом (уровень + тема + история сессии) → ответ
6. Запись в `messages` (role=`assistant`) в БД
7. ElevenLabs → mp3
8. Стриминг mp3 обратно клиенту, проигрывание

### Принцип изоляции audio layer

С первого дня весь голосовой пайплайн прячется за единым интерфейсом `ConversationProvider` со следующим API:
```
startConversation(sessionId, systemPrompt)
  → onTranscript(role, text)
  → onAudioChunk(buffer)
  → onEnd()
```

Всё, что находится «выше» этого интерфейса (UI, БД, разбор ошибок), не знает, как именно происходит разговор. Это позволит позже подменить реализацию на realtime без переписывания приложения.

### План возможной миграции на realtime

В будущем возможна миграция на OpenAI Realtime API или Gemini Live для более естественного диалога.

- **Сохранится без изменений (~60% кода):** схема БД, UI, профиль, выбор темы, разбор ошибок, системные промпты
- **Будет переписано (~30–40%):** клиентский audio capture (`MediaRecorder` → WebRTC), серверный endpoint (REST → WebSocket-релей), проигрывание (mp3 → streaming chunks), логика записи транскрипта в БД
- **Важная засада:** OpenAI Realtime API включает в себя LLM. В realtime-режиме нельзя свободно подменять модель собеседника. Для гибкости можно смотреть в сторону Gemini Live или ждать аналог от Anthropic.

## 4. Модель данных

Все таблицы располагаются в схеме `public`. Поскольку проект выделен под этот сервис, префиксы не нужны — у нас нет соседних таблиц, с которыми может быть коллизия.

### Таблицы

**`profiles`** — профиль пользователя
- `id` (uuid, PK, FK → `auth.users.id`)
- `name` (text)
- `native_language` (text, default `'ru'`)
- `italian_level` (enum: `A1`, `A2`, `B1`, `B2`, `C1`, `C2`)
- `created_at`, `updated_at`

**`sessions`** — сессии разговора
- `id` (uuid, PK)
- `profile_id` (uuid, FK → `profiles.id`)
- `topic` (text) — свободный ввод темы пользователем
- `started_at`, `ended_at` (timestamptz)
- `status` (enum: `active`, `completed`, `abandoned`)

**`messages`** — реплики в сессии
- `id` (uuid, PK)
- `session_id` (uuid, FK → `sessions.id`)
- `role` (enum: `user`, `assistant`)
- `content` (text) — транскрипт/текст реплики
- `audio_path` (text, nullable) — путь в Supabase Storage
- `created_at` (timestamptz)

**`errors`** — найденные ошибки (заполняется после завершения сессии)
- `id` (uuid, PK)
- `session_id` (uuid, FK)
- `original_quote` (text) — что сказал пользователь
- `correction` (text) — правильный вариант
- `explanation_ru` (text) — объяснение на русском
- `error_type` (enum: `grammar`, `lexicon`, `pronunciation`, `syntax`, `style`)
- `created_at`

**`summaries`** — общий итог сессии
- `id` (uuid, PK)
- `session_id` (uuid, FK, unique)
- `overall_comment` (text)
- `useful_vocabulary` (jsonb) — список фраз/слов из сессии
- `level_observation` (text) — комментарий о соответствии уровню
- `created_at`

**`api_usage`** — учёт расходов на внешние API (миграция 0002)
- `id` (uuid, PK)
- `profile_id` (uuid, FK → profiles)
- `session_id` (uuid, FK → sessions, nullable)
- `provider` (enum: `openai_whisper`, `openai_chat`, `anthropic_claude`, `elevenlabs_tts`)
- `operation` (text) — 'transcribe', 'respond', 'analyze', 'tts'
- `model` (text, nullable) — конкретная модель
- `input_units` (numeric) — токены/секунды/символы в зависимости от провайдера
- `output_units` (numeric) — токены ответа, 0 для не-LLM
- `cost_usd` (numeric) — посчитан на лету при вставке
- `created_at`

### Авторизация и RLS

- Используется `auth.users` из Supabase
- RLS включён на всех таблицах
- Политика: пользователь видит только свои строки (`auth.uid() = profile_id` или через JOIN на сессии)
- Триггер `on_auth_user_created` на `auth.users` авто-создаёт строку в `profiles` при регистрации (живёт в схеме `auth`)

### Storage

- Bucket `audio` (private)
- Структура: `{profile_id}/{session_id}/{message_id}.{webm|m4a}` — расширение зависит от клиентского кодека (iOS пишет m4a, остальные webm)
- Lifecycle policy: TBD (хранится бессрочно сейчас)

## 5. Конфигурация и секреты

### Новая система API-ключей Supabase

Все проекты, создаваемые с ноября 2025, используют новую систему ключей вместо легаси `anon` + `service_role`:

| Тип ключа | Формат | Где использовать |
|---|---|---|
| Publishable key | `sb_publishable_...` | Клиент, безопасно публиковать |
| Secret key | `sb_secret_...` | Только сервер (API routes), полный доступ, обходит RLS |

Ключи берутся в Supabase Dashboard: **Settings → API Keys**. Секретный ключ скрыт по умолчанию, нужно нажать **Reveal**. Минимум один секретный ключ обязан существовать — им пользуется сам дашборд.

### Переменные окружения

Файл `.env.local` (в `.gitignore`!):

```
# Supabase
NEXT_PUBLIC_SUPABASE_URL=https://xxx.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
SUPABASE_SECRET_KEY=sb_secret_...

# AI services
OPENAI_API_KEY=sk-...
ANTHROPIC_API_KEY=sk-ant-...
ELEVENLABS_API_KEY=...
ELEVENLABS_VOICE_ID=...
```

В Vercel те же переменные нужно прописать в **Project Settings → Environment Variables** перед первым деплоем.

### Технические нюансы новых ключей

- **Supabase JS SDK работает без изменений** — `createClient(URL, KEY)` принимает новые ключи прозрачно
- **`Authorization` header нельзя использовать** для publishable/secret ключей — только `apikey` header. SDK делает это автоматически; ручные fetch-запросы к Supabase REST API мы не пишем
- **Secret key в браузере = HTTP 401** — это защита от утечки. На клиенте только `NEXT_PUBLIC_*` переменные
- **Audit Log** — каждое использование секретного ключа логируется в дашборде, видно в `Settings → Audit Log` организации

### Лимиты безопасности

- Spending limits настроены в OpenAI, Anthropic и ElevenLabs (~$20/мес каждый на старте)
- Supabase Free tier: проект ставится на паузу после **7 дней неактивности**, данные сохраняются, но нужно вручную восстановить

## 6. Пользовательский поток

1. **Логин** через Supabase Auth (magic link на почту)
2. **Профиль:** просмотр/изменение CEFR-уровня
3. **Старт сессии:** страница со свободным полем «О чём поговорим?» (тема вводится текстом). Бот ничего не инициирует — после нажатия «Начать» пользователь сам делает первую реплику
4. **Активная сессия:** кнопка записи (push-to-talk), отображение текущего транскрипта (опционально), кнопка «Завершить и получить разбор»
5. **Итоги сессии:** список ошибок (цитата → правильный вариант → объяснение на русском), полезная лексика, общий комментарий по уровню
6. **История:** список прошлых сессий с возможностью открыть итоги любой из них

---

## 7. Формат разбора ошибок

После завершения сессии Claude Sonnet получает полный транскрипт и возвращает:

- **Список ошибок:**
  - Цитата того, что сказал ученик
  - Правильный вариант
  - Краткое объяснение на русском (какое правило, почему так)
  - Тип ошибки (грамматика / лексика / синтаксис / стиль / произношение)
- **Полезная лексика:** интересные/полезные слова и выражения, встретившиеся в сессии
- **Итоговый комментарий:** наблюдение о соответствии заявленному CEFR-уровню, на что обратить внимание

## 9. Стоимость и стратегии оптимизации

### 9.1 Текущий план: turn-based pipeline

Одна 30-минутная сессия (ориентировочно):

| Сервис | Стоимость |
|---|---|
| Whisper (STT) | ~$0.10 |
| GPT-4o (диалог) | ~$0.15 |
| ElevenLabs (TTS) | ~$0.30 |
| Claude Sonnet (разбор) | ~$0.10 |
| **Итого** | **~$0.65** |

### 9.2 Если в будущем мигрировать на realtime

Цены на май 2026 (быстро меняются — обязательно верифицировать на момент миграции).

**OpenAI Realtime (gpt-realtime-2):**
- Аудио-вход: $32 / 1M токенов
- Аудио-вход (кэш): $0.40 / 1M токенов
- Аудио-выход: $64 / 1M токенов
- Кодирование: 1 токен = 100 мс пользовательского аудио / 50 мс аудио ассистента
- **Реалистично: $0.18–0.46/мин без оптимизаций, $0.05–0.10/мин с кэшированием**
- 30-мин сессия: $5–14 без оптимизаций, $1.50–3 с кэшем

**Gemini 3.1 Flash Live:**
- Аудио-вход: $3 / 1M токенов (~$0.005/мин)
- Аудио-выход: $12 / 1M токенов (~$0.018/мин)
- В 4–10× дешевле OpenAI Realtime, голоса заточены под живой диалог
- **Реалистично: $1.50–4.50 за 30-мин сессию**

**Сравнение:**

| Подход | Стоимость 30-мин сессии |
|---|---|
| Turn-based (текущий план) | ~$0.65 |
| OpenAI Realtime без оптимизаций | $5–14 |
| OpenAI Realtime с кэшированием | $1.50–3 |
| Gemini Flash Live | $1.50–4.50 |

Вывод: realtime минимум в 2–5× дороже turn-based даже после оптимизаций. Если идти в realtime — Gemini Flash Live выглядит как явный фаворит по соотношению цена/качество для разговорной задачи.

### 9.3 Стратегии снижения стоимости realtime

1. **Prompt caching — главный рычаг.** Системный промпт строго в начале, без изменений в течение сессии. Динамические части (тема, имя ученика) — в конец. Снижает стоимость входных токенов до 90%. Кэш живёт 5–10 минут, длинные паузы между репликами ломают эффект.

2. **`retention_ratio < 1` при обрезке контекста (OpenAI).** По умолчанию сервер удаляет минимум сообщений при превышении контекста, но это «бьёт» кэш в начале разговора. Значение 0.8 удаляет на 20% больше, чем минимум — даёт запас перед следующей обрезкой и держит кэш дольше.

3. **Mini/Flash модели вместо флагманов.** `gpt-realtime-mini` и `gemini-3.1-flash-live` стоят кратно дешевле, а для бытового разговорного итальянского глубокое рассуждение не нужно.

4. **Гибридная архитектура.** Realtime — только для самого диалога. Постсессионный анализ остаётся на не-realtime Claude Sonnet (~$0.10/сессия). Это уже заложено в текущий план и переезжает на realtime без изменений.

5. **Жёсткий бюджет на сессию.** Мягкое предупреждение в UI на 25-й минуте, hard-stop на 45-й. Защита от случайного «забыл выключить» — особенно важна на realtime, где деньги «капают» постоянно.

6. **Короткие реплики бота.** Аудио-выход стоит вдвое дороже входа (1 токен на 50 мс против 100 мс пользовательского). Системный промпт «отвечай 1–3 предложениями, не выдавай длинных монологов» — это прямая экономия 30–50% на output.

7. **Кэш-дружественная структура промпта.** Статика (роль учителя, правила работы под CEFR, общее поведение) → динамика (конкретный уровень, тема, имя). Если добавится «учитывать прошлые ошибки» — этот блок тоже в конец, иначе на каждой сессии кэш-мисс.

### 9.4 Мониторинг

Обязательно настроить дашборды расходов в OpenAI, Anthropic, ElevenLabs (и Google, если перейдём на Gemini). Базовый лимит трат на уровне аккаунта — обязательно, как страховка от багов.

## 11. Особенности реализации (что выяснилось по ходу)

### Архитектурные решения, к которым пришли

**Email + Password вместо Magic Link.** Supabase Free tier строго лимитирует встроенный email (~3-4 письма/час). Для одного пользователя постоянная отправка magic link — лишняя точка отказа. Password-логин решает проблему полностью, magic link оставлен как fallback в раскрывающемся блоке на странице логина.

**Декаплинг завершения сессии и анализа.** Изначально Server Action `endSession` делала `update + analyze + redirect` в одной цепочке — это давало баг «кнопка ничего не делает» из-за длительного Claude-вызова, обрывающего Server Action. Решение: `endSession` только меняет статус и редиректит на summary, а сама страница summary детектит отсутствие `summaries`-строки и Client Component'ом запускает анализ автоматически с показом прогресса. Та же логика работает для кнопки «Переанализировать».

**Vercel Fluid Compute обязательно для analyze-session.** Без `export const maxDuration = 60` на этом route — Vercel Hobby даст функции только 5-10 секунд, и анализ упадёт. С Fluid Compute (включён по умолчанию для новых проектов) — до 60 секунд на бесплатном тарифе.

**Аудио-кодек выбирается на клиенте по `MediaRecorder.isTypeSupported`.** iOS Safari не поддерживает webm. Клиент сам определяет кодек (mp4/m4a на iOS, webm/opus на остальных) и сообщает серверу через FormData. API route использует переданное расширение для пути в Storage и Content-Type.

**Pre-warmed Audio для iOS autoplay.** iOS блокирует `audio.play()` если он не вызван в рамках user gesture. Между нажатием кнопки записи и моментом проигрывания ответа бота — несколько async-шагов, формально gesture-связь теряется. Решение: при первом старте записи создаётся и «разогревается» один Audio-элемент тихим WAV, потом переиспользуется для всех ответов в сессии.

### Гочи Supabase, на которые натыкались

**Серая иконка RLS = кэш UI**, а не реальное состояние. `pg_tables.rowsecurity` через SQL — единственный надёжный способ проверки. Cmd+R чинит индикатор.

**Триггеры на `auth.users` не видны в Dashboard → Triggers по умолчанию.** Этот раздел фильтрует по схеме `public`, а триггер на регистрацию пользователя живёт в схеме `auth`. Надо переключить селектор схемы наверху страницы.

**Новые API-ключи Supabase** (`sb_publishable_...` / `sb_secret_...`) работают идентично легаси для нашего use case, никаких изменений в коде не потребовалось. SDK прозрачно их принимает.

### Решения по UX

**Голосовой режим как push-to-talk, не VAD.** Принципиальное решение: пользователь сам контролирует, когда говорит. Это даёт право на паузы и обдумывание без срабатывания «end of speech» детектора.

**Тема — soft constraint в промпте.** Не сценарий и не чек-лист, а семантический якорь, задающий регистр и лексический пул. Бот может уходить в смежные темы естественным образом.

**Анализ показывается только когда готов.** На странице summary при отсутствии данных автоматически запускается анализ со спиннером — это лучше чем «пустая страница, нажмите кнопку».

### Лимиты сессии

Мягкое предупреждение (25 мин) — баннер с возможностью закрыть, отображается поверх UI (fixed, bottom-24 на мобиле, bottom-4 на десктопе). Hard-stop (45 мин) — `SessionTimer` вызывает `endSession()` напрямую; сервер обновляет статус и редиректит на summary, запуская стандартный flow анализа. Реализовано клиентским таймером (`setInterval`), базовая защита от «забыл выключить».

### Стоимость в реальной эксплуатации

Прикидка из секции 9.1 (~$0.65 за 30-минутную сессию) подтверждается. Основные траты — ElevenLabs (TTS) и GPT-4o, остальное копейки. Учёт ведётся в `api_usage`, страница `/stats` показывает агрегаты.

## 13. Принятые принципы

- **Один пользователь = простая инфраструктура.** Никаких многопользовательских заморочек, биллинга, тарифов.
- **Выделенный Supabase-проект.** Полная изоляция от других сервисов в том же аккаунте — нельзя случайно сломать соседний проект.
- **Изоляция audio layer.** Чтобы миграция на realtime была реалистичной, а не «переписать с нуля».
- **Никаких пресетов тем.** Свободный ввод гибче и не загромождает UI.
- **Ошибки разбираются в конце, не в процессе.** Не прерывать поток разговора — приоритет на свободу высказывания.
- **БД — единый источник истины.** И собеседник, и анализатор читают одну и ту же запись транскрипта.
